# 券商交易记录同步方案设计文档

> 创建日期：2026-03-14
> 状态：方案讨论中

---

## 一、背景

当前 Local Ledger 系统中的所有交易记录均由用户手动录入（`trade_trigger = MANUAL`）。随着交易频次增加，手动录入效率低下且容易出错。

**目标**：实现从券商平台 API 自动同步个人交易记录到系统中，减少人工操作，提升数据准确性。

### 问题 2：数据获取方式

不同券商提供的 API 接入方式差异较大，需要逐一评估：

#### 2.1 API 接入方式对比

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **券商官方 OpenAPI** | 通过 REST/WebSocket 直接调用券商 API | 实时性好、数据准确、可自动化 | 各家 API 差异大、需要逐一适配、可能有调用频率限制 |

**需要讨论**：

- 老虎证券使用 Tiger Open API（REST 方式）
- IBKR 已明确选用 **Flex Web Service**，用于首次历史回补和后续周期性同步

### 问题 4：同步策略

#### 4.1 触发方式

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **手动触发** | 用户点击"同步"按钮 | 简单、用户可控 | 需要用户主动操作 |
| **定时自动同步** | 系统后台定时任务（如每天收盘后） | 全自动、数据及时 | 需要调度框架、需处理异常重试 |
| **Webhook** | 券商推送交易通知 | 实时性最好 | 大部分券商不支持 |

**需要讨论**：
- [x] 初期是手动触发还是自动同步？
- [ ] 如果自动同步，频率多高？每天一次？每小时一次？
- [ ] 是否需要支持指定时间范围的手动同步？

**已决策**：
- **通过 REST API 手动触发**：提供一个 HTTP 接口，每调用一次就触发完整的同步逻辑。暂不做前端按钮和定时任务
  - 接口路径：`POST /api/broker-sync/trigger`
  - Controller 放在现有的 `controller/` 包中（统一管理，不在 `sync` 包内），如 `controller/BrokerSyncController.java`
- Phase 1 核心逻辑包括：数据获取（调用券商 API）→ 反序列化为券商专属模型 → **日志输出**（在券商专属模型层打印日志，供核对原始数据）
- **暂不做统一模型转换**：先聚焦于 API 对接和券商原始数据的获取与验证，统一模型（`BrokerTradeRecord`）的定义和映射逻辑留到后续阶段
- **暂不入库**：当前数据库中为真实数据，不能被污染。同步过来的数据先通过打印日志的方式输出，方便后续核对验证。确认数据准确无误后，再接入入库逻辑
- 定时同步等高级触发机制后续再补充

#### 4.2 增量同步机制

**需要讨论**：
- [ ] 如何标记同步进度？（上次同步时间戳？上次同步的最后一条记录 ID？）
- [ ] 券商 API 是否支持增量查询？（按时间范围/按游标翻页？）
- [ ] 同步的时区如何处理？（券商所在时区 vs 用户本地时区 vs UTC）

#### 4.3 幂等性与去重

这是同步功能中最关键的问题之一。

**需要讨论**：
- [ ] 如何唯一标识一条交易记录，防止重复导入？
  - 券商是否返回唯一交易 ID？
  - 如果没有唯一 ID，用哪些字段组合作为去重依据？（交易日期 + 证券代码 + 交易方向 + 数量 + 价格？）
- [ ] 重复记录的判定阈值？（完全一致才算重复？还是近似匹配？）
- [ ] 发现重复时的处理策略？（跳过？更新？提醒用户？）

#### 5.1 字段映射

|-----------------|------|---------|---------|

| `brokerId` | Long | 固定值，取决于同步的目标券商 | 如何自动匹配？ |
| `assetType` | AssetType | 需要从券商返回的证券信息中推断 | 不同券商分类标准不同 |

| `name` | String | 券商返回的证券名称 | 可能为英文/中文，是否需要标准化？ |

| `tradeType` | TradeType | 从券商的买卖方向映射 | |

### 问题 6：凭证管理与安全

#### 6.1 认证信息存储

券商 API 需要认证凭证（API Key、Secret、Token 等），如何安全管理？

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **配置文件** | 存在 `application.properties` 或环境变量中 | 简单 | 明文存储、不够安全 |
| **数据库加密存储** | 加密后存入专用的凭证表 | 可管理多个凭证 | 需要加解密逻辑、密钥管理 |
| **操作系统密钥链** | 利用 macOS Keychain / Linux Secret Service | 安全性高 | 平台相关、部署复杂 |

**需要讨论**：
- [x] 考虑到这是个人项目（本地运行），安全级别需要到什么程度？
- [ ] 凭证是全局配置（一个券商一套凭证），还是需要支持多账户？
- [ ] Token 过期后如何刷新？是否需要 OAuth 流程？

**已决策**：

**凭证放在配置文件中管理**，复用现有的 `application-local.properties` 机制，与数据库密码等敏感信息保持一致的管理方式。

理由：项目处于早期阶段，不做过多复杂设计（不引入数据库加密存储、不用系统密钥链等），保持简单直接。

具体方案：

1. **`application.properties`** 中放默认占位配置（空值），作为配置项声明：
   ```properties
   # ========== 券商 API 凭证 ==========
   # 老虎证券
   broker.tiger.tiger-id=
   broker.tiger.private-key=
   ```

2. **`application-local.properties`** 中填写真实的凭证值（已被 `.gitignore` 排除，不会提交到代码仓库）：
   ```properties
   broker.tiger.tiger-id=your_tiger_id_here
   broker.tiger.private-key=your_private_key_here
   ```

3. **`application-local.properties.template`** 中补充券商配置的示例，方便日后参考：
   ```properties
   # 券商 API 凭证 - 老虎证券
   broker.tiger.tiger-id=your_tiger_id_here
   broker.tiger.private-key=your_private_key_here
   ```

4. 在 Spring Boot 中通过 `@ConfigurationProperties(prefix = "broker.tiger")` 注入到配置类中

#### 6.2 券商 API 访问架构

| 方案 | 说明 |
|------|------|
| **后端直连** | Spring Boot 后端直接调用券商 API | 
| **通过本地代理** | 部分券商（如盈透）要求运行本地网关，后端通过网关访问 |

**需要讨论**：

**需要讨论**：
- [x] 是否采用适配器模式（Adapter Pattern）来屏蔽各券商 API 差异？
- [ ] 同步日志/历史是否需要持久化？
- [ ] 是否需要引入消息队列或异步处理？（考虑到是个人项目，可能不需要）

**已决策**：

**1. 采用适配器模式（策略模式 + 适配器模式组合）**

通过统一接口 `BrokerSyncAdapter` 屏蔽各券商 API 差异，新增券商只需实现接口并加 `@Component`，无需修改任何现有代码。

**2. sync 作为顶级独立包**，与 `service/controller` 等 Web 层平级，内部自成体系，不依赖 Web 层的分层结构。

**3. 中间模型分层策略**

每个券商有自己独立的专属记录模型（如 `TigerOrderRecord`），用来承载从券商 API 获取后的原始数据在内存中的中间状态。原因：
- 各券商 API 返回的字段差异很大，用一个通用模型硬塞所有券商的字段会很别扭
- 保留原始语义——券商特有的字段在各自的模型中保持清晰含义
- 方便调试和核对——日志打印时能看到券商原始数据的完整面貌

**日志打印位置：在券商专属模型层打印**，而非转换为系统统一模型之后。这样可以直接跟券商平台上的记录核对，排查问题时也能定位是 API 返回有问题还是映射逻辑有问题。

**4. 数据流设计**

```
券商 API 响应 (JSON)
    ↓ 反序列化
券商专属模型 (如 TigerOrderRecord)     ← 每个券商各自定义，保留原始字段
    ↓ 📋 日志打印（Phase 1 在此输出，核对原始数据）
    ↓ （后续阶段再实现）
系统统一模型 (BrokerTradeRecord)        ← sync 模块的统一输出模型
    ↓ （后续阶段再实现）
入库 / 其他处理
```

#### 7.2 数据模型扩展

**已决策** — 详见 [data-persistence-design.md](./data-persistence-design.md)

| 表/字段 | 用途 | 决策 |
|---------|------|------|
| `broker_sync_batches` | 通用同步批次元信息表 | ✅ 需要，记录每次同步的起止日期、记录数、状态等 |
| `ibkr_staged_orders` | IBKR 核心暂存表（Order 粒度，两阶段导入的中间存储） | ✅ 需要，按券商独立一张暂存表，粒度为订单级 |
| `ibkr_staged_trade_confirms` | IBKR 执行明细附表（可选，用于审计/对账） | ⚠️ 可选，非核心流程必须 |
| `trade_records.external_id` | 券商原始订单 ID（IBKR 的 `orderID`），用于去重和区分数据来源 | ✅ 需要，`NULL` 表示手动录入 |
| `trade_records.external_broker` | 来源券商标识，与 `external_id` 配对 | ✅ 需要，方便关联查询对应券商暂存表 |
| `trade_records.sync_batch_id` | 同步批次 ID，用于追溯 | ✅ 需要，FK→`broker_sync_batches` |

**已决策**：
- [x] 是否需要同步批次表？ → **需要，`broker_sync_batches` 通用表**
- [x] `trade_records` 表是否需要增加 `external_id` 字段？ → **需要，同时加 `external_broker` 冗余字段**
- [x] 是否需要 `sync_batch_id`？ → **需要，FK 关联批次**
- [x] `trade_trigger` 是否新增 `BROKER_SYNC` 枚举值？ → **否**，`trade_trigger` 描述"交易为什么发生"，不描述"记录来源"；通过 `external_id IS NULL` 区分手动录入和同步导入

### 问题 8：冲突处理与数据修正

同步数据可能与已有手动录入的数据产生冲突。

#### 8.1 冲突场景

| 场景 | 说明 | 处理策略待定 |
|------|------|------------|
| 完全重复 | 同步的记录与手动录入的完全一致 | 跳过？标记关联？ |
| 部分不一致 | 日期/数量/价格等大部分一致，个别字段不同 | 以哪边为准？提醒用户？ |
| 手动记录缺失 | 券商有记录但系统没有 | 直接导入？ |
| 系统多出记录 | 系统有记录但券商没有 | 是否标记异常？ |

**需要讨论**：
- [ ] 已有手动录入的记录，同步时遇到对应记录如何处理？
- [ ] 是否需要一个"同步预览"功能，让用户确认后再真正导入？
- [ ] 是否需要支持"以券商数据为准"批量覆盖已有记录？

#### 8.2 数据修正

**需要讨论**：
- [ ] 同步导入的记录是否允许用户手动修改？
- [ ] 如果允许修改，下次同步时如何处理？（覆盖用户修改？跳过已修改记录？）
- [ ] 是否需要记录"原始同步数据"和"用户修改后数据"两个版本？
