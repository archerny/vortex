# 交易费用保留来源精度，前端仅展示两位小数

## 背景与目标

IBKR 导入已经用字符串构造 `BigDecimal`，按 `abs(commission) + abs(tradeCharge)` 计算费用，没有主动舍入；但正式表 `trade_records.fee` 和实体声明为两位小数，落库会丢失来源精度。

用户于 2026-11-17 明确：数据库和后端费用计算完整保留小数精度；前端仍展示两位小数，展示结果不得写回账本。此前 Tiger 历史费用没有超过两位，不做历史数据修复、重新同步或重算。本方案仅针对费用，不调整成交价、成交金额、平均成本或汇率的现行精度。

## 范围与历史决策

沿用 [0013 IBKR 暂存与映射](0013-2026-04-21-ibkr-staging-schema.md) 的原始文本暂存、订单粒度、费用绝对值相加及既有币种口径，沿用 [0018 导入一致性](0018-2026-04-22-broker-import-consistency-v2.md) 的事务和整批失败处理。补充正式费用列与编辑链路的无损精度约定，不修改历史方案正文。

## 设计与取舍

- 新增 V29 迁移，将共享正式费用列改为 PostgreSQL 不指定 precision/scale 的 `NUMERIC`。同步实体的列声明，保留非空、默认值及非负约束。在 PostgreSQL 支持的数值范围内不按固定小数位舍入；Tiger 和手工交易同样使用此列。
- 后端继续使用 `BigDecimal` 原值及数据库 `SUM`，不引入浮点转换、`setScale` 或有限精度 `MathContext`。费用组成与正负号映射保持原规则。
- 保留现有 JSON 数字字段 `fee`，新增只读十进制字符串 `feeExact`，供编辑无损回填。现有调用方兼容；请求中的 `fee` 继续由 Jackson 绑定为 `BigDecimal`，支持数字或十进制字符串。统计值仍由后端完整精度汇总后输出。
- 列表、详情和统计继续显示两位小数。新增、编辑的费用输入使用 Ant Design `InputNumber` 的 `stringMode`，不设置固定小数位，不把编辑值转换为 JavaScript `Number`。编辑回填优先使用 `feeExact`，兼容旧响应的 `fee`；表单编辑时显示原始费用，保存时发送原始十进制字符串，避免仅修改其他字段就损失费用精度。
- 不改变其他金额字段的 API 类型或处理方式，不增加依赖。来源值的数值相等为验收口径，不要求数据库保存文本形式的尾零。

## 验证与验收

- 合成 IBKR 订单覆盖 8 位、超过 8 位、极小费用、相加进位、零和缺省费用，确认计算和 API JSON 往返无损；确认旧数字 API 与新增字符串字段兼容。
- 交易新增、更新及费用统计的纯内存测试使用 Mockito 仓储，验证后端不降低费用精度。前端用合成数据确认超出 JavaScript 有效精度的费用通过编辑回填和提交仍完整，显示格式不参与提交。
- 使用 Flyway 验证空库 V1→V29，以及 V28 加入两位合成历史费用再升级至 V29，确认原值不变；通过真实 ORM 保存、读取高精度费用并汇总对账，确认列无固定 scale，非空／非负／默认值约束继续生效。
- 验证迁移失败在事务内回滚、可重试，且 Flyway 再次迁移无待执行项。所有数据库数据均为可丢弃的合成记录，单元测试不连接数据库。
- 运行相关后端单测、前端单测与构建、文档链接检查和 `git diff --check`。记录实际命令、环境、退出状态及未覆盖部分。

## 发布与失败处理

先应用 V29，再让新应用导入高精度费用；Flyway 在应用启动时执行迁移，需为 ALTER TABLE 留出锁等待窗口。迁移不修正、重新下载或重放历史交易，旧两位费用的数值保持不变。

V29 失败时由 PostgreSQL/Flyway 事务回滚，排除失败原因后重试；不修改已应用迁移、不执行自动降精度回滚。应用回退时保留扩展后的列，不能直接改回两位而损失新费用精度。
