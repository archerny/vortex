# 历史成本回放在清仓时结清成本池

## 背景与目标

证券代码变更通过 `MarketEventProcessingService.calculateAverageCost` 回放旧证券的历史交易，确定系统生成的 SELL/BUY 记录价格。当前卖出时先将平均成本舍入至 6 位再扣减成本池，持仓全部卖出时仍可能留有尾差。例如成本 50,000、持仓 30,000，按均价 1.666667 扣减后剩余 -0.01；随后买入一股、金额 10，代码变更时得到 9.9900。

本次修复历史回放中“清仓后重新建仓受到旧成本尾差影响”的缺陷。用户认为现有历史记录没有问题，本次不连接账本数据库、不发起历史事件重算，也不改写已存交易。

## 范围与历史方案

沿用 [0002 市场事件处理](0002-2026-03-08-market-event-processing.md) 的移动加权平均法、按证券与券商计算成本、事件事务与系统交易生成流程。该历史方案关于清仓后自然归零的说明仅以整除成本举例，本方案明确不能整除时也必须结清。历史方案保留原样。

仅修改成本回放在多头持仓恰好全部卖出时的分支，并增加内存回归测试。普通交易、IBKR 费用、部分卖出精度、代码变更计价精度、持仓聚合、数据库结构与 API 均不变。此处成本池是回放中的局部变量，不是另一个持续存储的账本账户。

## 设计与关键取舍

- 买入继续将原交易金额加入成本池，数量累加，不改变费用是否计入成本的现有口径。
- 当前回放持仓大于 0，且本次 SELL 数量恰好等于该持仓时，直接将成本池置零，并扣减数量至零，不再用舍入均价扣减。最后一笔清仓结清全部剩余成本，后续 BUY 从零成本池开始。
- 部分卖出仍使用现有 6 位 HALF_UP 均价扣减，最终返回均价仍为 4 位 HALF_UP；本次不定义新的分摊精度或成本转移金额规则。
- 只匹配数量相等，不能把卖超持仓一律当作清仓；现有负持仓、卖空或跨零处理不在本次修复范围内。
- 回放继续按仓储提供的日期顺序处理，证券代码变更只处理事件前一天的正持仓。本次不引入新的同日成交顺序口径。

## 验证与验收

- 原始复现：买入 10,000 股、金额 10,000，再买入 20,000 股、金额 40,000，清仓后以金额 10 买入一股；代码变更生成的两笔系统交易均为数量 1、价格 10.0000、金额 10，不再出现 9.9900。
- 覆盖一次卖完、多次部分卖出后卖完、多轮清仓再建仓、负尾差和正尾差，以及零成本的市场事件派生股参与回放。验证尾差不会累积到新持仓。
- 验证未清仓时的移动加权均价结果保持原规则，完全没有持仓时不生成代码变更交易，按证券与券商隔离，不污染历史输入对象。
- 测试调用真实的事件处理、持仓计算与成本回放逻辑；所有 Repository 使用 Mockito，不启动 Spring 容器或数据库。仅验证本次重新建仓场景的转移成本正确，不宣称已解决所有均价舍入造成的成本转移精度问题。
- 使用 `.dev-environment.local.md` 的 `ubuntu-dev`，既有 Java/Maven、离线缓存，JVM 临时目录 `/tmp`、构建产物 `backend/target/`。运行新增测试及相关 `PositionServiceTest`、`TradeRecordServiceTest` 等服务回归，记录命令与退出状态。
- 执行 `git diff --check` 与文档链接检查。因涉及账本成本回放，按 AGENTS.md 进行独立复核。单测不替代真实数据库事务验证；本次不重算或验证用户历史账本。
