# 测试执行、日志诊断与 Token 脱敏回归优化

## 背景与目标

用户希望缩短反复测试的耗时、减少成功日志带来的阅读及 Token 开销，且不降低回归覆盖。本方案按用户要求合并本次尚未提交的原 0044 性能研究、0045 关键路径研究和 0046 无真实等待回归方案，统一保留决策、实现、运行证据和限制。

沿用 [0039 测试维护](0039-2026-11-17-test-suite-maintenance.md) 的覆盖原则及 [0024 Token 脱敏](0024-2026-11-12-ibkr-token-log-redaction.md) 的安全契约。用户最终选择两 JVM；Token 脱敏回归无需真实等待，也不增加客户端返回耗时断言。

## 最终设计与改动范围

- 后端 Surefire 默认使用 **2 个测试 JVM**、复用进程，将测试输出保存到 `backend/target/surefire-reports/*-output.txt`；参数通过 Maven 属性配置，允许命令行覆盖。前端保持 Vitest 的现有默认文件并行。
- 测试命令保留 **`-e`**，使 Maven 构建／启动失败时输出异常栈和 `Caused by`。正常测试的预期异常日志仍写入文件；成功时只向工具或对话返回汇总，失败再读原日志。保留 stdout、stderr 和原始退出码。
- `IbkrFlexClient.sleep(long, String)` 由 private 改为包内可见，方法实现、调用位置和生产构造保持原样。成功的 Token 回归用 Mockito Spy 仅跳过该方法的实际休眠，覆盖初始等待及可能出现的限流等待；HTTP 使用原 Mock。
- 保留原两项客户端用例、真实 `fetchReport` 路径、两阶段请求携带原 Token、日志脱敏、返回内容及非法 URL 异常链断言。不改生产等待、重试、限流或中断处理，不验证客户端墙钟返回耗时。
- 同步 `docs/unit-test-spec.md`、README 测试入口、IBKR 当前知识及设计索引。本次没有依赖、数据库迁移、业务口径、公共 API、历史数据或部署变更。

当前代码改动为 POM 测试执行配置、客户端等待方法的内部可见性和成功测试的等待替换。真实券商的 5 秒初始等待、3 秒重试间隔、1.1 秒请求间隔继续保留。相较通用等待／时钟注入，本次使用最小测试入口，符合用户只优化脱敏场景的范围。

## 调查范围与验证方法

清点 31 个后端源测试类和 6 份前端测试；扫描等待、共享状态、应用启动、日志捕获及跳过配置。完整阅读后端 `SyncResultTest`、`SyncBatchFailureHandlerTest`、`SyncBatchRecoveryRunnerTest`、`IbkrFlexClientTest`、`IbkrDuplicateBatchTest`、`IbkrReportStructureTest`、`FlexQueryParserTest`、`PositionServiceTest`、`MarketEventProcessingServiceTest`、`OrderedMarketEventRegressionTest` 及全部前端测试，核对客户端、失败处理器、解析器、结果模型、相关前端实现、配置和历史文档；完整阅读两个 Python e2e 启动器。

本次没有逐项重审全部业务实现，不声称全部 541 项均无冗余。运行范围为纯内存单测；未执行 e2e、迁移、实际事务／并发、浏览器或前端构建，未访问真实数据库、券商或个人 XML。不同验证层次的用例不互相替代。

2026-11-18，默认环境为 Lima `ubuntu-dev`：Ubuntu 26.04.1、4 CPU／约 4 GiB、Java 25.0.5（编译目标 17）、Maven 3.10.0、Surefire 3.1.2、Node 26.13.0、npm 11.20.0、Vitest 1.6.1。执行路径为当前工作树 `/home/bytedance.guest/workspace/private/vortex`，沿用已有工具与缓存，`TMPDIR=/tmp`、`MAVEN_OPTS=-Djava.io.tmpdir=/tmp`，没有安装工具。

独立对照顺序执行，避免 CPU 或报告目录竞争。用 `time.monotonic()` 测量命令墙钟时间，原输出落盘。后端按本轮 `Running` 套件读取 XML，比较完整类／方法名、嵌套及参数化实例，同时核对套件实际启动次数和最终汇总，排除旧报告与重复执行。前端比较 JSON 中每个文件和完整案例名称。

以下可比全量均为 31 个源类、91 个实际套件、541 个唯一案例，无失败／错误／跳过。前端各对照均为 6 文件、54 项。暖运行没有 `clean`、安装或重编译；客户端修改后的第一次专项包含编译，不能把该命令总耗时直接当作等待收益。

## 实测结果及最终选择

| 阶段／配置 | 各次完整后端墙钟时间 | 判断 |
| --- | --- | --- |
| 优化前：单 JVM、默认日志 | 15.137、14.537 秒；均值 **14.837 秒** | 原始暖运行基线 |
| 只重定向日志 | 14.133、14.983 秒；均值 14.558 秒 | 时间差仅约 1.9%，主要改善输出 |
| 两 JVM、重定向，Token 测试仍真实等待 | 11.309、10.816 秒；均值 11.062 秒 | 当时约快 25.4% |
| Token 测试取消实际休眠，后续两 JVM 对照 | 9.020、8.870 秒；均值 **8.945 秒** | 最终推荐 |
| 同一优化版本，三 JVM | 9.420、9.139 秒；均值 9.279 秒 | 比两 JVM 略慢 |
| 同一优化版本，四 JVM | 9.836、9.582 秒；均值 9.709 秒 | 比两 JVM 更慢 |

最后六次按 **2／3／4／4／3／2** 的顺序运行，源码指纹一致，命令仅改变 `forkCount`，均无重编译；541 项逐项一致，套件各执行一次。

客户端改动的直接前后对照使用同一两 JVM 命令：全量墙钟 **10.527→9.125 秒**，客户端类执行时间 **5.192→0.217 秒**。原两个专项方法也以同命令通过，类执行时间为 **5.777→0.693 秒**。客户端实现、原断言及四次验收证据经未参与实现的 Agent 独立复核，未发现本次引入的可行动问题；该复核只读源码及已有证据，没有另启真实环境或重跑 Maven。

### 为什么增加 JVM 没有继续改善

原四 JVM 的命令中，首批类在第 1.87～1.93 秒开始，客户端到第 **4.86 秒**才开始并真实等待 5 秒，第 **10.16 秒**结束；其他所有类第 **6.74 秒**已完成，命令第 **10.52 秒**退出。总耗时由最晚完成的执行链决定，单个用例的等待无法除以 JVM 数量。

取消客户端等待后，主要拖尾变为 [整批清理失败场景](../backend/src/test/java/com/vortex/sync/adapter/ibkr/IbkrDuplicateBatchTest.java)，仍执行两次各 2 秒的真实退避。更多 JVM 增加首次 Mock、类加载和组件初始化工作，无法缩短这段串行等待。

原版本四 JVM 补充实验：默认顺序均值 10.408 秒；`balanced` 首次无统计 10.290 秒，后两次均值 9.518 秒；固定 seed 33 将慢类放入首批为 10.077、8.516 秒，再预加载现有 Mockito agent 为 8.380、8.752 秒，未证明稳定额外收益。预加载同时影响父 Maven 与测试 JVM，仅为控制实验。单独一个 JVM 运行客户端、其余三个 JVM 运行其他测试的分组也未改善：正确分组的并行阶段约 10.925 秒，含预编译共 12.496 秒。

不固化随机种子、预加载 agent 或专用客户端 JVM。历史统计模式会产生本地 `.surefire-*`，实验新增文件已复制到忽略目录后清理。首次专用分组使用显式 `*Test` 通配符导致部分嵌套类重复执行，校验拒绝该结果；改为精确顶层类名单后，2＋539 项无重复或遗漏。

### 前端、日志与退出诊断

前端默认两次为 5.121、4.536 秒；线程数 2／1／4 的单次为 5.844／6.139／4.845 秒，forks pool 两进程为 4.557 秒，未显示超过默认的明确收益。默认断言合计约 88 ms，主要时间在加载真实 `antd`、图标和组件依赖；没有通过关闭隔离或替换展示组件获得速度。

默认后端日志约 **1.341 MB、12,341 行**，重定向后控制台约 **22.4 KB**，字节量减少约 **98.3%**。原输出约 84.3% 是异常标题／堆栈，13.6% 是同步、解析及清理日志。大量异常由失败路径测试主动模拟，断言通过时不代表构建失败。完整测试输出保留在类日志及对应 XML 的 `testcase/system-out/system-err`，并行控制台行可交错，按类／方法名定位。

受控启动失败验证使用不存在的测试 JVM 路径：默认命令保留错误摘要，加 `-e` 后包含完整 Maven 调用栈和 `Caused by`，两次退出均为 1。JVM 尚未启动时可能只有原生诊断，没有 Java 异常栈；日志捕获保留 stdout／stderr。不要用没有 `pipefail` 的 `mvn … | tail` 判断 Maven 状态。

早期归档的 94 秒及 Surefire 30 秒退出确认等待不是本轮提速基线。旧转储位于 `ForkedBooter.acknowledgedExit → acquireOnePermit`；本轮可比测试未复现，不能归因于业务线程泄漏或宣称已修复。再出现时保留父／子 JVM 同期转储、dumpstream、完整命令及最后套件时间，不降低退出超时掩盖问题。

## 耗时与 Token 节省估测

**测试耗时：** 从原均值 14.837 秒到最终两 JVM 均值 8.945 秒，估计每轮减少 **5.892 秒、约 40%**，完成同一测试集的速度约为原来的 **1.66 倍**。这是当前机器已有缓存和编译产物的估测，不含首次下载、完整重编译、e2e 或调查本身的多次试验。

**日志 Token：** 98.3% 是控制台字节量降幅，不是已计量的整轮 AI Token 降幅。按约 4 字符／Token 粗算，若整份日志原样输入模型，约 **33 万→5,600 Token**，每次日志输入理论上少约 **32.9 万、约 98%**；异常栈分词与中文比例会使估值变化，未使用模型计量器实测。

**当前工作流：** 本轮优化前后的测量脚本都已经把完整日志落盘，只返回约几百字符的汇总，成功一次返回模型的日志约 **100～300 Token**。在这个相同摘要流程中，减少日志字节量带来的额外 Token 节省估计**接近 0%**。工具原先存在截断时也不能按完整日志推算；整次研发任务还包含代码、文档、工具调用与推理，缺少计量数据，不能据此声称整体少 98%。

**方案阅读：** 合并前三份正文共约 1.18 万字符，合并后约 0.6 万字符，文档阅读 Token 粗估减少 **约 50%**。这是阅读这些方案的成本降幅，不是整次研发任务总 Token 的降幅。

## 实施、验收与证据

1. 将 Surefire 默认两 JVM、日志重定向配置到 POM 的可覆盖属性，测试入口保留 `-e`；不启用 JVM 内方法并行。
2. 保留已完成的客户端等待替换和原两项安全回归，不改变生产构造、重试／限流／中断路径。
3. 使用默认命令完整执行 541 项，并验证命令行覆盖和日志诊断；核对实际清单、启动次数、退出码和日志保留。源码未变的有效结果可复用。
4. 按用户要求将本轮三个方案合并为当前文件，更新知识、运行说明及全部受影响链接，检查新增文件和 `git diff --check`。

默认使用：

```sh
mvn -e -f backend/pom.xml test
```

完整缓存时可加 `-o`。诊断时仍可通过 `-DforkCount=1`、`-Dmaven.test.redirectTestOutputToFile=false` 覆盖默认选项。输出文件和缓存不提交。

本次默认配置验收：`mvn -e -o -f backend/pom.xml test` 退出 0，541 项清单与原记录逐项一致，套件各启动一次；按本轮 XML 中的 JVM 启动信息确认两个测试 JVM，墙钟 8.783 秒。覆盖参数的客户端／SyncResult 专项执行 8 项、退出 0，确认单 JVM 和应用控制台输出恢复；受控启动失败退出 1，保留完整错误栈及 `Caused by`。当前默认值生效，`-e` 继续由测试命令指定。

本地原始证据位于被忽略的 `backend/target/test-performance/`：原基线／输出为 `backend-default-*`、`backend-redirect-*`；调度为 `schedule-*.log/json`、`schedule-analysis.json`；正确专用分组为 `client-dedicated-2*`；启动诊断为 `startup-failure-*`；客户端前后为 `token-no-wait-{before,after}-{focused,full}.log/json`、`token-no-wait-comparison.json`、`token-no-wait-independent-review.json`；最终并行度为 `token-optimized-fork*-*.log/json`、`token-optimized-fork-matrix.json`。所有统计使用本轮实际清单，不能将不同阶段的通过数量重复累加。

默认配置、覆盖和启动诊断的最终日志为 `test-optimization-{default,override,startup-failure}-final.log/json`。

后续仍值得优化整批清理回归的真实退避；需保留清理次数、CLEANUP_FAILED、成功历史保留、中断及失败处理断言，另行实施并独立复核。当前两 JVM 选择和客户端优化不代表已经完成该项或修复已知 Flex 错误码问题。
