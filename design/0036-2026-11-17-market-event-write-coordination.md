# 顺序事件与历史锁的事务协调

## 背景与目标

[0035](0035-2026-11-17-ordered-market-events-and-history-locks.md) 已确认关联证券历史锁、顺序处理、同日关联拒绝和受限撤销。本补充确定实施中的数据库互斥方式，保持业务范围与计算规则不变，不创建锁定日期表。

## 设计与取舍

- 所有正式账本短写事务共用一个 PostgreSQL 事务级 advisory lock：在读取可变对象和检查历史边界前取得，随事务提交／回滚释放。采用现有 EntityManager 的同一事务连接，不持有跨请求或跨同步批次的锁。
- 这只串行化短写入，不把历史锁扩大到无关证券；历史边界仍从已处理、未撤销的关联事件推导。相比维护多证券锁集合，此实现避免漏锁新旧证券与死锁顺序问题，适合先保证一致性；并发吞吐不是本次优化目标。
- 手工交易增改删、三类事件增改撤销、事件单次处理、同步批次创建、IBKR／Tiger 正式导入、IBKR 关联回填及批次清理均参与同一协调。不得在持锁的外层事务中调用另一个需要该锁的 REQUIRES_NEW 事务，避免自身等待；原导入 Worker 保持每条独立事务。
- 历史检查统一在 Service 完成。合法重复仍校验并跳过，新增锁定历史明确失败。已处理事件字段不可原地改写；MARKET_EVENT 派生行不允许经普通 CRUD 改动。
- 事件处理仍使用现有金额、数量及前一日基准，单次只生成本事件记录；撤销只清理本事件的 MARKET_EVENT 行。没有数据库结构变更、历史自动修复或启动重算。
- HTTP 写入冲突保留 status/message，补充稳定错误代码和阻挡事件元数据，返回 409；同步通过既有 UNRECOGNIZED 分类保留失败原因。

## 实现与验证

1. 先补原服务入口的回归并在旧实现确认失败，再增加统一边界服务与短写互斥，替换级联处理。
2. 更新调用方、纯内存测试的依赖及页面撤销交互，不改变已有数量、费用与成本断言。
3. 在隔离临时 PostgreSQL 中通过真实 Spring 事务、JPA 仓储及合成数据验证拒绝、提交／回滚、并发检查与同步批次互斥；运行结束停止并清理临时集群。单测全部模拟 Repository，不操作数据库。
4. 前端验证冲突反馈、撤销交互及构建；按清单完成相关后端测试，独立复核实现、运行证据和完整差异。

## 影响、失败与文档

等待中的写入在持锁事务结束后重新检查最新边界。冲突在正式写入前拒绝，后续生成或持久化失败时由事务回滚。存量状态仍需按 0035 核对，不宣称 processed=true 证明历史结果正确。实际账本不在本次运行验证范围内。

实现后同步 market-events、trades-and-positions、同步生命周期与恢复说明，以及 TODO 完成记录。0035 正文保持原样；本补充把其中多证券锁获取的实施设想改为单个数据库短写互斥，避免引入独立锁表及其维护状态。
